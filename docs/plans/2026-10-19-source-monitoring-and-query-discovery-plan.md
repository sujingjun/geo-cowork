## 3. 同一来源，分开产出三种结果

| 结果 | 核心问题 | 可进入的内容 | 不能自动推出 |
| --- | --- | --- | --- |
| 需求与 Query 发现 | 用户想完成什么，遇到什么障碍，希望得到什么答案？ | 可追溯的明确提问、由原始经历支持的隐含问题；GSC/PAA/生成问题另标来源 | 发帖热度就是市场需求；媒体作者建议就是用户问题；隐含归纳是原话 |
| 品牌舆情与信任观察 | 公众对品牌、体验、承诺和责任主体有什么新增陈述或变化？ | 用户投诉/好评、营销声明、官方回应、评分变化、独立支持与反证 | 投诉即事实、账号关联即品牌指使、评分变化即服务质量变化 |
| 公开知识一致性 | 公开资料与已确认知识是否冲突、过期、遗漏或缺少支持？ | 官网、应用资料、PR、媒体/博客、第三方聚合页与已确认知识的对照 | 外部网页出现错误即消费者平台已回答错误；文件不一致必然构成法律或合规结论 |

需求发现继续区分 **品牌问题线**（明确涉及 MyyShop）与 **领域问题线**（成长/变现等非品牌需求）；领域问题按成长和首次变现分主题。舆情可以同时产生待确认 Query，但不自动加入固定监测组。

同一原帖或评论可以同时支持需求与舆情分析，引用同一个原始记录。各视图可展示它，汇总“独立证据数”时不能因被分到两类就重复计数。

既有报告含品牌方采购、已变现创作者、不同国家或语言的信号。这些可以保留为相邻领域观察，但首期 Query 选择仍须对照已确认的目标人群与美国/英语场景；不能把历史报告里的全部问题无筛选导入首批 Query Set。

## 4. 信源状态与结果数量分开

历史 `available / partial / not_configured / unavailable / no_new_signal` 保留在历史报告中。新的用户视图建议分开呈现以下维度，避免把“没配置”“没读到”和“检查后没新增”都写成 0：

| 维度 | 用户应看到的结果 |
| --- | --- |
| 实体与配置 | 已绑定具体社区/页面/app/package/账号范围，或尚未可靠确认实体 |
| 访问与原文 | 读到目标原文、仅元数据、被阻断、原文不可核验，以及具体原因 |
| 声明范围内的覆盖 | 已检查哪些对象和窗口、哪些内容缺页/未返回/尚未检查；公开搜索样本不写成全平台覆盖 |
| 本轮结果 | 合格新增用户内容数、首次发现的历史内容数、既有事项更新数、无合格新增或无法评估 |
| 下一步 | 可恢复的读取、需要补充的实体/授权/数据，及受影响的分析范围 |

这是产品展示建议，不直接新增运行 Schema。落地时复用现有 Source 与 Research Manifest 的 `access_state`、`original_content_state`、snapshot/hash 等合同；原文缺失不能通过显示层改名变成 captured。

## 5. 从监控内容到 Query 候选

1. **确认来源身份和本次范围。** 在已有 Source 上复用 URL/app/package 等稳定身份，附加本次检查用途、对象和时间窗；未确认实体的来源只报告配置缺口。
2. **保存可追溯原始记录。** 至少能定位平台、原始对象/URL、原文或必要摘录、发布时间及其依据、首次观察时间和本次取得时间。缺失时间或原文如实标明；平台授权与保留要求决定可保存的内容范围。
3. **区分三种时间语义。** 窗口内发布且首次纳入的是本窗口新增；更早发布但本次首次找到的是新发现的历史内容；旧记录新增回复、修正、状态或声明是事项更新。不得把搜索引擎本次返回旧帖等同新发帖。
4. **去重并保留关联。** 优先按平台原生帖子/评论/review ID 和稳定页面身份去重，规范化 URL 辅助，内容指纹用于识别转载/近似重复。相同事件的多次转述保留传播关系，不直接算独立证实；同一用户对同一问题的重复回复不累加独立用户证据。
5. **按内容用途分流。** 广告/招募/教程/媒体观点不计普通用户问题；其中的品牌承诺或公开冲突仍可进入舆情。真正的问题或亲历障碍进入候选；隐含问题标为分析归纳，保留支撑原文。
6. **记录受众、地区和语言。** 按 20A，英文且地区未知的线索可以保留，和原文明确自述/标注美国的线索区分；未知不靠语言、用户名或社区推断。需要为美国监测组加条件时，标为研究设定。收入阶段和品牌方/创作者角色也按可见内容记录，未知则未知。
7. **整理最终问句。** 按 21A，保留原文，另生成去身份化、可独立理解的 Query；同意图且关键条件相同才合并并保留全部来源，影响答案的条件不同则分开。非品牌组不插入 MyyShop，翻译/改写/新增条件可回溯。
8. **形成可审阅候选。** 展示主题、意图、受众适配、原始来源、观察/生成类型、选择理由、知识可回答部分、未知能力和排除理由。可采样与可评价分别判断，不要求每个观察问题都已有完整品牌答案。
9. **用户确认版本化 Query Set。** 确认实际发送文本及包含范围后才进入 OneGlanse 的采样计划。新发现不静默改变已有冻结集合或比较分母。

历史报告的导入从第 2 步开始补齐证明：只有对话摘要而没有原始定位/快照时，保留“历史报告线索”。从来源找到的证据与生成的探索问题分别标识，不用模型补写缺失帖子来凑足来源数。

## 6. 问题族、趋势与舆情变化

沿用历史日报对趋势的证据要求：没有可复算、同口径的比较数据时，不输出 `rising` 排名。2026-10-18/19 的报告均明确指出，历史运行次数虽超过七次，但问题族语义、来源覆盖或独立用户去重尚未完成同口径核验。

- 问题族的定义与版本要可追溯，合并/拆分影响须记录；不能今天合并、明天拆分后直接比较计数。
- 分别列内容条数、独立用户/事件数、来源数；一名用户提到六个平台仍不是六条独立用户证据。无法核对独立性时标未知。
- 新问题族、新发现历史问题、重复问题、上升问题和舆情事项更新分别表达。首次发现一条问题可以报告，不能据此称市场趋势。
- 比较必须说明窗口、来源范围、采样方式和覆盖变化。某来源从不可用恢复后数量增加，先解释覆盖变化，不能直接称需求上涨。
- PAA、GSC、社区观察与模型生成数量不混为同一频率指标。具体基线长度、增长阈值和置信度口径继续访谈，不把“七份日报”直接当作七次可比观察。
- 舆情同时记录原文事实、当事人陈述、尚未核实的关系、独立支持、反证和当前处置。历史 P0/P1/P2 标签仅保留为历史评级，当前评级规则与人工责任待确认。
- 旧报告没有新增证据，不代表已报告的投诉已解决；评分回升也不能代替个案解决证据。第三方声明是否被消费者 AI 采用，需由对应答案样本另行观察。

## 7. 与现有插件职责衔接

| 环节 | 复用入口 | 本轮实际状态 |

| 消费者平台答案采集 | `geo-answer-cycle`、OneGlanse MCP | 接收已确认 Query 的采样；OneGlanse 不因这份计划自动承担社交评论/媒体舆情采集 |

当前已有美国 App Store 与 Influencer Marketing Hub 的 canonical Source 可作为身份对接起点；存在 Source 不等于已经抓取最新内容或取得持续访问能力。旧 `knowledge/00-governance/source-register.md` 仍含模板行，不能用它假装已有全量监控配置。

## 8. 操作手册必须呈现的结果

用户使用顺序为：配置/核对全量信源清单与输入方式 → 查看可用性和具体缺口 → 插件执行来源检查、接收原 ChatGPT 报告，或组合使用 → 统一核验与去重 → 查看新增/历史新发现/事项更新 → 审阅成长/变现候选与品牌问题 → 确认 Query Set → OneGlanse 采样 → GEO 诊断与舆情处理。

每次运行至少能查看：

- 全量信源矩阵和各自窗口，包含未配置、不可用、部分结果及未执行项；
