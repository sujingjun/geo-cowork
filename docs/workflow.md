# SDD人机协同工作流

## 1. 核心流程

所有需求按照以下流程推进：

```text
原始诉求
→ 产品需求文档（PRD）
→ 系统规格（Spec）
→ 实施计划（Plan）
→ 任务拆解（Tasks）
→ 代码实现
→ 测试验证
→ 发布上线
→ 复盘改进
```

SDD 的核心控制面是仓库中的文档、代码和验证记录。

ChatGPT、Codex、GitHub 都是可选协作工具：

- 可以全部由 Codex 完成；
- 可以由 ChatGPT 负责共创和设计，Codex 负责实现；
- 可以由 Codex 主导，ChatGPT 按需审查；
- 可以使用 GitHub Issue、PR，也可以完全在本地完成。

无论使用哪种方式，都必须遵守相同的文档、状态和验收要求。

---

## 2. 文档职责、目录与权威

`docs/workflow.md` 是本仓 SDD 流程、文档分类、状态与交接规则的唯一细节来源；`docs/README.md` 只负责导航当前入口，不复制或改变本章规则。

| 文档         | 位置                   | 唯一职责                                             | 不得替代                               |
| ------------ | ---------------------- | ---------------------------------------------------- | -------------------------------------- |
| 工作流规范   | `docs/workflow.md`     | 定义研发链路、文档分类、状态、交接与完成规则         | 项目宪法、产品需求或技术契约           |
| 文档导航     | `docs/README.md`       | 指向当前权威入口、现有目录和迁移说明                 | 原始需求、批准、实现或验证证据         |
| 架构设计     | `docs/architecture/`   | 说明系统目标形态、模块关系和待批准架构决策           | `AGENTS.md`、已批准 PRD/Spec 或 Record |
| 原始需求     | `docs/requirements/`   | 如实记录业务诉求、问题、约束、来源和待确认假设       | PRD、Spec 或批准结论                   |
| 产品需求文档 | `docs/prd/`            | 定义用户、场景、价值、业务规则、业务验收与非目标     | 系统实现方案或验证事实
| 产品产品交互原型| `docs/prototypes/`            | 最终形态交互原型和里程碑交互原型    | 系统真实交互                    |
| 系统规格     | `docs/specs/`          | 定义系统行为、接口、数据、边界、异常和非功能要求     | 产品批准、实现或生产验收               |
| 实施计划     | `docs/plans/`          | 定义技术方案、实施顺序、迁移、测试、发布策略和验收门 | 已批准 Spec、实际执行结果或发布授权    |
| 任务清单     | `docs/tasks/`          | 定义可独立执行、验证和交接的最小工作单元             | Plan、Record 或人类批准                |
| 验证记录     | `docs/records/`        | 记录实际命令、结果、失败、修复、证据范围和未验证项   | Spec、Plan、批准或整体生产就绪结论     |
| 运维手册     | `docs/runbooks/`       | 定义部署、监控、告警、恢复和回滚操作                 | 发布授权或实际发布记录                 |
| 发布记录     | `docs/releases/`       | 记录版本、影响范围、授权、实际发布与已知限制         | 业务效果或复盘结论                     |
| 复盘记录     | `docs/retrospectives/` | 记录上线结果、问题、假设证伪和改进项                 | 原始验证证据或批准后的行为变更         |
| 经验沉淀     | `docs/lessons/`        | 记录可复用经验、反模式和适用边界                     | 项目当前事实、Spec 或 Record           |
| 交接记录     | `docs/handoff/`       | 支持未完成、阻塞或跨 Session 的任务继续执行          | Task 状态、Record 或批准决策           |
| 项目知识库   | `docs/wiki/`           | 提供架构、产品模块、领域和术语的可追溯导航摘要       | 规范、批准、实现或验证的原始证据       |

### 建档、命名与迁移规则

1. 目录在首次出现 canonical 文档时创建；不提交空目录，也不为目录整齐复制同一内容。
2. 既有文档保留原路径和历史语义，不因本规范批量改名或回填状态。只有实质性改写时，才补齐本节要求的元数据和关联链接。
3. 新建或实质性修改的 PRD、Spec、Plan、Task、Record、Handoff、Runbook、Release、Retrospective 与 Lesson 在标题后必须清楚标出：状态、创建或更新时间、来源或关联工件、适用范围。Record 还必须标出工作目录、基线/分支和任务范围。
4. 时间性工件使用 `YYYY-MM-DD-<topic>.md`：需求、PRD、Plan、Task、Record、Handoff、复盘和经验；Spec 保持 `NNNN-<topic>.md`；Runbook 使用 `<system>-<operation>.md`；Release 使用 `v<version>.md`；Wiki 使用稳定、语义化的页面名。

### Wiki 规则

`docs/wiki/` 只收录可追溯的导航摘要，不复制 canonical 文本，也不把摘要升级成批准、实现或验证事实。每个 Wiki 页面（包括 `index.md`）必须使用以下 YAML Frontmatter，并由 `docs/wiki/index.md` 索引：

```yaml
---
title: <页面标题>
kind: index | architecture | product | domain | glossary | decision
status: proposed | approved | implemented | verified | blocked | not_applicable
sources:
  - <仓库相对 canonical 路径或已授权 URL>
updated: YYYY-MM-DD
---
```

Wiki 的导航读取顺序固定为：`docs/wiki/index.md` → 页面 Frontmatter → 正文。原始来源变更而未同步时，页面必须标明过期或更新 `updated`，不得静默沿用旧结论。

### 知识库-first + 源码验证

项目知识库（`docs/wiki/`，以及存在时的图谱）只作为导航与关系发现层。处理代码库、架构、文件关系或项目内容时，先从知识库定位候选模块、来源和调用路径；在给出结论、实施修改或评审风险前，必须回到当前工作区的实际源码核验定义、调用点、配置以及必要的行号，并按风险核验测试、日志或运行时证据。

源码与当前工作区状态优先于知识库。发现知识库过期、缺失或与源码不一致时，必须明确说明；在当前任务范围内更新知识库，或以源码结论为准并记录待同步项。知识库关系不能代替源码证据，也不能把推断关系表述为已验证事实。

发生冲突时，按以下顺序处理：

```text
当前用户明确指令
→ AGENTS.md
→ 已批准 PRD
→ 已批准 Spec 与不冲突的已批准架构决策
→ 已批准 Plan
→ Task
→ 已验证 Record（仅在其明确记录的事实范围内）
→ Handoff
→ Wiki、历史讨论和外部参考
```

Spec 与架构设计发生实质冲突时，不得依靠上述顺序静默选择；必须记录冲突、停止受影响实现并请求决策。Wiki、Handoff 和历史讨论不能提升其来源的状态。

## 3. 状态定义

只使用以下状态：

- `proposed`：已提出，尚未批准；
- `approved`：已批准，可以实施；
- `implemented`：实现已经存在，尚未完成全部验证；
- `verified`：要求的验证已经实际执行并通过；
- `blocked`：存在明确阻塞；
- `not_applicable`：经确认不适用。

禁止：

- Agent 自行批准 PRD 或 Spec；
- 把代码存在视为 `verified`；
- 把单元测试视为运行时验证；
- 把本地验证视为生产可用；
- 把上线成功视为业务目标已经达成。

发布、部署成功、生产指标观察和业务效果必须作为 Release、Record 或 Retrospective 中的可追溯事实与门禁结果记录，不得另造 `released`、`validated` 等状态词。`verified` 只说明 Record 中声明范围内的检查确实完成，不自动代表发布或业务目标达成。

## 4. 产品需求文档（PRD）

PRD 负责回答：

```text
为什么做
为谁做
解决什么问题
用户如何使用
业务规则是什么
业务上如何验收
明确不做什么
```

PRD 不负责定义：

- 数据库表；
- 中间件选型；
- 类和函数；
- 代码目录；
- 具体技术实现。

进入 Spec 前明确：

- 问题；
- 目标用户；
- 业务目标；
- 用户流程；
- 业务规则；
- 验收标准；
- 范围外事项；
- 待确认问题。

---

## 5. 系统规格（Spec）

Spec 是代码实现和测试验收的共同依据。

Spec 明确：

- 触发条件；
- 输入和输出；
- 状态机；
- 合法和非法状态变化；
- 接口及 Schema；
- 错误码；
- 数据约束；
- 幂等规则；
- 并发处理；
- 事务和一致性；
- 超时、重试和补偿；
- 权限、安全和审计；
- 性能、容量和可用性；
- 正常、异常和边界场景。

实现过程中发现 Spec 缺口时：

```text
停止受影响实现
→ 更新 Spec
→ 更新测试
→ 获得批准
→ 更新 Plan 和 Tasks
→ 继续实现
```

---

## 6. 实施计划（Plan）

Plan 根据已批准 Spec 定义：

- 当前系统现状；
- 目标与现状差距；
- 技术方案；
- 架构和模块改动；
- 数据库与迁移；
- 外部依赖；
- 事务、一致性和补偿方案；
- 测试策略；
- 监控和告警；
- 灰度、发布和回滚；
- 风险；
- 实施顺序；
- 验收门。

---

## 7. 任务拆解（Tasks）

每个任务必须包含：

```text
任务编号
对应 PRD、Spec 和 Plan
任务目标
成功标准
范围外事项
前置依赖
目标文件
测试要求
验证命令
风险
当前状态
涉及的 Session 与 Handoff（如有）
```

每个任务应尽量同时包含必要的：

```text
数据
业务逻辑
接口
测试
验证
```

需要跨 Session、需要独立验收或需要交接的任务必须创建 `docs/tasks/` 文档。短小且可在当前会话闭环的任务可以直接以当前用户指令和 Record 为准，但仍必须在 Plan 或 Record 中保留目标、验证和范围边界。一个任务可以跨多个 ChatGPT 或 Codex Session。

---

## 8. 开始任务

开始实现前必须：

1. 阅读 `AGENTS.md`；
2. 阅读对应 PRD、Spec、Plan 和 Task；
3. 阅读最近的 Record 和 Handoff；
4. 明确：

```text
本次目标
成功标准
范围外事项
已有实现
待实现内容
主要风险
授权限制
未验证项
```

不得覆盖、删除或整理与当前任务无关的改动。

---

## 9. 实现规则

默认实施顺序：

```text
先建立失败测试或验收测试
→ 实现最小行为
→ 运行相关测试
→ 补充异常和边界场景
→ 运行完整检查
→ 更新 Record
```

实现时必须遵守：

- 每个行为能够追踪到 Spec；
- 测试验证 Spec，而不是当前代码写法；
- 不做无关重构；
- 不自行扩大范围；
- 不自行降低 Spec；
- 不把业务规则隐藏在 Prompt、配置或代码常量中；
- 不绕过模块公开接口；
- 不静默修改数据语义；
- 默认使用脱敏 fixture 和 Fake Model；
- 不调用未经授权的真实外部系统。

---

## 10. 测试与验证

测试至少覆盖：

```text
正常场景
非法输入
边界条件
重复调用
并发冲突
依赖失败
超时
重试和补偿
权限与隔离
进程重启与恢复
```

验证分为：

1. 静态检查：格式、代码规范、类型、构建和治理检查；
2. 单元测试：规则、Schema、状态机和边界；
3. 集成测试：数据库、Redis、队列、迁移和适配器；
4. 端到端测试：完整业务流程、故障、重启和恢复；
5. 业务验收：根据 PRD 验证用户和业务结果；
6. 生产验证：灰度、监控和真实运行指标。

测试来源：

```text
PRD → 业务验收
Spec → 功能、异常、边界和性能测试
Plan → 架构、迁移、故障和发布验证
Task → 单任务完成检查
```

---

## 11. 验证记录（Record）

每个产生实现、验证或结论的 Task 更新 `docs/records/` 中的 Record，并且只记录实际执行结果：

```text
任务编号
当前状态
代码基线和分支
实际变更
实际执行命令
退出码
测试结果
首次失败和修复
已验证内容
未验证项
风险
下一步
```

不得补写未执行的命令，不得把推测写成验证事实。

Record 必须链接对应 Task、Plan 和 Spec/PRD（如适用），但不能反向修改这些工件的需求、批准或状态；发现冲突时应新增待决事项或回写上游工件。

---

## 12. 发布上线

发布前必须准备：

- Release Notes；
- Runbook；
- migration 顺序；
- 监控和告警；
- Feature Flag 或关闭开关；
- 灰度策略；
- 停止条件；
- 回滚方案；
- 发布后检查项。

推荐发布流程：

```text
预发验证
→ 小流量灰度
→ 观察技术和业务指标
→ 扩大流量
→ 全量
→ 更新发布 Record
```

没有明确授权不得部署或发布。

---

## 13. 复盘改进

上线或任务完成后必须根据实际结果复盘：

- 目标是否达成；
- PRD 的问题定义是否准确；
- Spec 是否遗漏场景；
- Plan 的技术方案是否成立；
- Tasks 是否拆分合理；
- 测试遗漏了什么；
- 发布、监控和回滚是否有效；
- 哪些假设被证伪；
- 哪些经验可以复用。

根据问题来源反哺：

```text
产品问题 → 更新 PRD
系统行为缺口 → 更新 Spec
技术方案问题 → 更新 Plan
任务拆分问题 → 更新 Tasks
测试遗漏 → 更新测试规范
通用经验 → 写入 Lessons Learned
```

复盘发现的问题必须形成新的任务，不得静默修改已经批准的行为。

---

## 14. Session 交接

任务需要跨 Session 继续、被阻塞或需要交给他人时，必须在 `docs/handoff/` 留下 Handoff；已关闭且无需继续的任务以 Record 作为收口，不重复制造 Handoff：

```text
任务编号
Session ID
当前状态
本次完成内容
实际修改
实际验证
关键决策
主要风险
未验证项
当前分支和工作区状态
下一步
下一 Session 开场指令
```

后续 Session 必须先读取 Task、最近 Record 和最新 Handoff（如有），不依赖模型记忆继续工作。

## 15. 协作模式

### Codex 独立模式

Codex 可以完成：

```text
需求分析
→ PRD
→ Spec
→ Plan
→ Tasks
→ 代码实现
→ 测试
→ Record
→ 发布准备
→ 复盘
```

遇到产品范围、架构、安全、真实资源和发布决策时，必须请求人类批准。

### ChatGPT 与 Codex 协同

ChatGPT 通常负责：

- 需求共创；
- PRD、Spec 和 Plan；
- 架构与安全审查；
- 代码、测试和 Record 验收。

Codex 通常负责：

- 仓库分析；
- Tasks；
- 代码实现；
- 测试验证；
- Record；
- Handoff。

二者通过仓库文档和 Handoff 同步，不依赖历史聊天记录。

### GitHub 协作

GitHub 可以用于：

- Issue；
- Branch；
- Pull Request；
- CI；
- Review；
- Release。

GitHub 不是强制依赖。不使用 GitHub 时，可以通过本地 Git、Task 文档、Record 和 Handoff 完成相同流程。

---

## 16. 授权边界

可以自主执行：

- 阅读仓库；
- 编写 PRD、Spec、Plan 和 Tasks；
- 修改本地代码；
- 使用脱敏 fixture；
- 使用 Fake Model；
- 运行本地测试；
- 更新 Record 和 Handoff。

必须获得明确授权：

- 将 PRD 或 Spec 标记为 `approved`；
- 读取真实用户或企业数据；
- 调用真实或付费模型；
- 调用真实第三方 API；
- 写入外部业务系统；
- 修改云资源或远端 CI；
- 删除不可恢复的数据；
- commit、push 或创建 PR；
- merge、部署和发布；
- 切换生产流量；
- 提升 Agent 自动执行权限。

授权仅适用于当前明确范围，不能跨 Task 或 Session 自动继承。

---

## 17. 完成定义与门禁

任务标记为 `implemented`：

- 实现已经存在；
- 已在 Task、Plan 或 Record 中说明本次变更范围、实际检查和未验证项；
- 可能已有部分检查通过，但尚未完成其所需的 Runtime、业务或生产验证；
- 不代表上游 PRD/Spec 已批准，也不代表任何阶段门通过。

任务标记为 `verified`：

- 对声明的成功标准，所需检查已实际执行并在 Record 中可复现地记录；
- 正常、非法和边界场景，以及适用的迁移、Runtime、权限和人工检查均已通过；
- 上游批准、产品验收、Shadow 或生产门仍按其自身适用范围单独判断，不能由本状态跳过。

发布只在 Release/Record 证明发布材料、当次授权、目标环境部署和发布后检查均已完成时成立；业务效果只在 Retrospective/Record 证明观察与复盘均已完成时成立。二者都不是额外状态词，也不能由静态检查或文档存在替代。
